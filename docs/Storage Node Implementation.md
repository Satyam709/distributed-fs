# Storage Node Implementation

---

## 1. Chunking Strategy

### Approach: Fixed Size Chunking

Split every file into equal sized pieces before upload. The client owns this entirely — no server involvement in chunking.

- **Default chunk size:** 4MB (configurable)
- **Chunk count:** `ceil(file_size / chunk_size)`
- **Last chunk:** smaller than 4MB, that is fine

### Chunk ID Generation

```
chunk_id = SHA256(file_id + chunk_index)
```

- `file_id` — UUID generated by client before upload starts
- `chunk_index` — 0, 1, 2 ... N, determined by client during split
- Client computes all chunk IDs **locally before talking to metadata**
- IDs are deterministic and positional — no content reading needed to generate them

### Why This Approach

- Chunk IDs known upfront → client can give metadata the full plan in one call
- No deduplication (acceptable for this project — write-once model)
- Simple reassembly — chunk_index is implicit position in file record array
- Fixed size → predictable parallelism math for upload and download

## 2. Client Local Manifest

Before uploading a single byte, client writes a local manifest file:

```
manifest.json
  file_id:     "uuid-abc123"
  filename:    "video.mp4"
  file_size:   104857600
  chunk_size:  4194304
  chunks:
    0 → chunk_id: "ab12...", status: pending
    1 → chunk_id: "9fd3...", status: pending
    2 → chunk_id: "cc44...", status: pending
    ...
```

Used for resumable uploads — if upload fails halfway, client reads manifest, skips already-done chunks, retries only pending ones. Deleted after successful `CommitFile`.

## 3. Upload Flow (End to End)

```
CLIENT                        METADATA                   STORAGE NODES
  │                               │                            │
  │  split file into 4MB chunks   │                            │
  │  generate file_id (UUID)      │                            │
  │  compute all chunk_ids        │                            │
  │  write local manifest         │                            │
  │                               │                            │
  ├──CreateFile(file_id,          │                            │
  │   filename, [chunk_ids])─────►│                            │
  │                               │  run placement strategy    │
  │◄──placement per chunk─────────│  return primary + replicas │
  │   {chunk_id: [NodeA,B,C]}     │  per chunk                 │
  │                               │                            │
  │  (upload chunks in parallel)  │                            │
  │                               │                            │
  ├──PutChunk(chunk_0)──────────────────────────────────►NodeA │
  ├──PutChunk(chunk_1)──────────────────────────────────►NodeB │
  ├──PutChunk(chunk_2)──────────────────────────────────►NodeA │
  │                               │                            │
  │                               │ NodeA fans out replication │
  │                               │ NodeA→NodeB, NodeA→NodeC   │
  │                               │                            │
  │◄──success per chunk───────────────────────────────────────-│
  │                               │                            │
  │  update manifest status       │                            │
  │                               │                            │
  ├──CommitFile(file_id)─────────►│                            │
  │◄──ack─────────────────────────│                            │
  │                               │                            │
  │  delete local manifest        │                            │
```

**Key rules:**

- Client uploads to primary node only — never directly to replicas
- Primary handles P2P fan-out to replica nodes concurrently
- `CommitChunk` is called by the **storage node**, not the client — metadata only records confirmed durable state
- `CommitFile` is called by the client only after all chunks are committed
- Metadata does not touch chunk bytes at any point

## 4. Download Flow

```
CLIENT                        METADATA                   STORAGE NODES
  │                               │                            │
  ├──GetFile(file_id)────────────►│                            │
  │◄──[chunk_id → live nodes]─────│                            │
  │                               │                            │
  │  (download all chunks in parallel)                         │
  │                               │                            │
  ├──GetChunk(chunk_0)──────────────────────────────────►NodeA │
  ├──GetChunk(chunk_1)──────────────────────────────────►NodeC │
  ├──GetChunk(chunk_2)──────────────────────────────────►NodeB │
  │                               │                            │
  │◄──chunk bytes (streamed)──────────────────────────────────-│
  │                               │                            │
  │  verify checksum per chunk    │                            │
  │  reassemble in chunk_index order                           │
```

- Client picks any live replica per chunk — can load balance across nodes
- Reassembly uses `chunk_index` ordering stored in file record
- Checksum verified client-side after each chunk received

## 5. Chunk Storage on Disk

### Directory Layout

Two-level sharding to avoid filesystem inode limits:

```
/data/
  chunks/
    ab/12/ab12fe93....chunk
    9f/d3/9fd3bc01....chunk
    cc/44/cc44de22....chunk
  tmp/
    ab12fe93....tmp       ← in-flight writes land here
  checksums.db            ← BoltDB: chunkID → checksum
```

First 2 chars of chunk_id → first subdirectory. Next 2 chars → second subdirectory. 256 × 256 = 65536 possible subdirectories — scales to millions of chunks.

### Write Strategy

```
1. Open .tmp file in /data/tmp/
2. Stream frames to .tmp, compute SHA256 simultaneously (single pass)
3. fsync .tmp
4. Rename .tmp → final .chunk path  (atomic on Linux)
5. Store checksum in checksums.db
```

Atomic rename means a crash mid-write never leaves a corrupt visible chunk. Either the full chunk exists or nothing does.

### Chunk Lifecycle States (implicit, no explicit state field)

| State | Indicator |
| --- | --- |
| Receiving | `.tmp` file exists |
| Complete | `.chunk` file exists, checksum in index |
| Corrupted | `.chunk` exists but verify fails |
| Evicted | File absent entirely |

## 6. Storage Node — Components

```
StorageNode
  ├── ChunkStore (interface)
  │     └── DiskChunkStore (implementation)
  ├── ChecksumIndex (BoltDB)
  ├── ChunkWriter (per-write session)
  ├── ChunkReader (per-read session)
  ├── PeerDialer (gRPC connection pool)
  ├── ReplicationManager
  │     └── repair job queue (buffered channel)
  │     └── repair worker pool (goroutines)
  │     └── RetryPolicy
  ├── HeartbeatSender
  └── gRPC Server
        ├── StorageServiceHandler
        └── ReplicationServiceHandler
```

### ChunkStore Interface

Methods: `Write`, `Read`, `Delete`, `Exists`, `Verify`, `List`, `FreeSpace`, `Size`

Keep it an interface — swap in an in-memory implementation for tests without touching any logic above it.

### ChecksumIndex

BoltDB backed. Stores `chunkID → SHA256 checksum` locally on each node. Avoids recomputing SHA256 on every verify request. Buckets: `checksums`.

### ChunkWriter

One instance per active write. Responsibilities:

- Accept frames one at a time, write to `.tmp`
- Hash incrementally per frame — no second read of file
- `Finalize(expectedChecksum)` — compare computed vs expected, rename to final path on match
- `Abort()` — delete `.tmp` file, called when stream dies mid-transfer or checksum fails

### ChunkReader

One instance per active read. Reads `.chunk` file in 32KB frames, returns each frame with `isLast` flag. Used by both `GetChunk` (client download) and `ReplicateChunk` (peer transfer) — same primitive.

### PeerDialer

gRPC connection pool to other storage nodes.

- `RWMutex` — many concurrent goroutines read, rare writes (new connections)
- Double-check pattern after acquiring write lock — prevents duplicate dials
- Health check on cached connection before returning — re-dials on `TransientFailure`
- gRPC keepalive params with `PermitWithoutStream: true` — detects dead peers in ~13s instead of OS default ~7min
- `Remove(address)` — evicts dead node's connection from pool
- `CloseAll()` — graceful shutdown

### ReplicationManager

Core P2P engine. Two entry points, one underlying primitive.

**Upload path:** `ReplicateToNodes(chunkID, targets, mode)`

- Fans out to all targets concurrently via goroutines
- Collects results with timeout (30s)
- Evaluates quorum — needs majority of targets to succeed
- Sync mode: client waits for all replicas before success
- Async mode: fires goroutines, returns immediately after primary write

**Repair path:** `EnqueueRepair(job)` → consumed by worker pool

- Buffered channel of 256 repair jobs
- 4 worker goroutines consuming queue
- Same underlying `replicateToSingleNode` primitive as upload path

**Concurrency control:** semaphore (buffered channel) limits max concurrent outbound streams to 8. Prevents disk and network saturation.

**RetryPolicy:** exponential backoff with jitter

- 3 attempts, 500ms base, 10s max, 2x multiplier
- Jitter on each sleep — prevents thundering herd when many chunks fail simultaneously
- Respects context cancellation — stops retrying if context is done

### HeartbeatSender

Ticker goroutine every 3 seconds. Sends `nodeID`, `freeSpace`, `chunkCount`, `timestamp` to metadata. Clean stop via `stop` channel. On unrecognized node_id in response, triggers re-registration.

### StorageNode (root)

Wires all components. Startup sequence:

1. Initialize `DiskChunkStore` — creates directory structure
2. Initialize `ChecksumIndex` — opens BoltDB
3. Initialize `PeerDialer`
4. Initialize `ReplicationManager`
5. Connect to metadata cluster
6. `RegisterNode` — send chunk inventory for reconciliation
7. Start `HeartbeatSender`
8. Start repair workers
9. Start gRPC server

Shutdown sequence:

1. Stop `HeartbeatSender`
2. `DeregisterNode` with metadata
3. `GracefulStop` on gRPC server — drains active RPCs
4. `CloseAll` on `PeerDialer`

## 7. gRPC Contracts

### MetadataService (clients + storage nodes → metadata)

| Method | Caller | Input | Output | Notes |
| --- | --- | --- | --- | --- |
| `CreateFile` | Client | file_id, filename, file_size, [chunk_ids] | placement per chunk (primary + replicas) | Runs placement strategy, stores file→chunks in FSM |
| `GetFile` | Client | file_id | file metadata + chunk list with live node addresses | Filters dead nodes from replica lists |
| `DeleteFile` | Client | file_id | ack | Marks deleted, enqueues eviction jobs |
| `ListFiles` | Client | optional filter | list of file metadata | Read-only FSM scan |
| `CommitChunk` | Storage node | chunk_id, node_ids, checksum | ack | Updates FSM with confirmed replica nodes |
| `GetChunkLocations` | Client | chunk_id | live node list | Used during download |
| `ReportCorruption` | Storage node | chunk_id, node_id | ack | Removes node from replica list, triggers repair |
| `RegisterNode` | Storage node | node_id, address, free_space, chunk_inventory | ack + confirmed node_id | Adds to NodeRegistry, schedules reconciliation |
| `DeregisterNode` | Storage node | node_id | ack | Marks draining, triggers repair for its chunks |
| `Heartbeat` | Storage node | node_id, free_space, chunk_count, timestamp | ack + optional repair instructions | Updates in-memory NodeWatcher only — NOT through Raft |
| `ReportRepairFailure` | Storage node | job_id, chunk_id, error | ack | Updates job status, re-enqueues with different source |

**Note on Heartbeat:** repair jobs are piggybacked on heartbeat response — metadata never needs to open a connection to storage nodes for routine work.

---

### StorageService (clients → storage nodes)

| Method | Type | Caller | Input | Output | Notes |
| --- | --- | --- | --- | --- | --- |
| `PutChunk` | Client streaming | Client | frames: chunk_id, file_id, index, offset, data, is_last, checksum, replicate_to (on first frame) | success, bytes_written, checksum confirmed | Triggers replication fan-out after finalize |
| `GetChunk` | Server streaming | Client | chunk_id, offset, max_bytes | frames: data, offset, is_last | ChunkReader streams in 32KB frames |
| `DeleteChunk` | Unary | Metadata | chunk_id | ack | Eviction — idempotent, not an error if already gone |
| `VerifyChunk` | Unary | Metadata | chunk_id, expected_checksum | valid bool, actual_checksum | Reports corruption if mismatch |

---

### ReplicationService (storage node → storage node, internal only)

| Method | Type | Caller | Input | Output | Notes |
| --- | --- | --- | --- | --- | --- |
| `ReplicateChunk` | Bidirectional streaming | Primary storage node | frames: chunk_id, offset, data, is_first, is_last | per-frame ack + final response (success, checksum) | Bidirectional for flow control — receiver acks frames, sender slows if receiver overwhelmed |

Client never calls this. Metadata never calls this.

```
Client
  ├── MetadataService.CreateFile       before upload
  ├── MetadataService.GetFile          before download
  ├── MetadataService.CommitFile       after all chunks done
  ├── MetadataService.ListFiles        browse
  ├── MetadataService.GetChunkLocations  during download

  ├── MetadataService.RegisterNode     on startup
  ├── MetadataService.DeregisterNode   on shutdown

  ├── MetadataService.CommitChunk      after replication complete
  ├── MetadataService.ReportCorruption when verify fails
  ├── MetadataService.ReportRepairFailure when repair job exhausts retries

Metadata Node (as gRPC client)
  ├── StorageService.DeleteChunk       eviction instructions
  └── StorageService.VerifyChunk       periodic integrity checks
```

## 8. P2P Replication Flow

### Upload Path (client-triggered)

```
1. Client streams chunk to primary (NodeA) via PutChunk
2. NodeA: ChunkWriter receives frames, hashes simultaneously
3. NodeA: Finalize — verify checksum, fsync, atomic rename
4. NodeA: ReplicationManager.ReplicateToNodes([NodeB, NodeC])
5. NodeA: fans out two goroutines concurrently
     goroutine 1: PeerDialer.Get(NodeB) → ReplicateChunk stream
     goroutine 2: PeerDialer.Get(NodeC) → ReplicateChunk stream
6. NodeA: ChunkReader streams file in 32KB frames to each peer
7. NodeB, NodeC: same ChunkWriter pipeline — tmp → hash → finalize
8. NodeB, NodeC: send final ACK on stream
9. NodeA: collects results, evaluates quorum
10. NodeA: MetadataService.CommitChunk([A, B, C])
11. NodeA: returns success to client
```

### Repair Path (metadata-triggered)

```
1. Metadata detects under-replicated chunk (node death)
2. Metadata piggybacks repair instruction on next heartbeat response to source node
3. Source node: RepairManager.EnqueueRepair(job)
4. Repair worker picks job: same replicateToSingleNode primitive
5. Source node: MetadataService.CommitChunk on success
6. Source node: MetadataService.ReportRepairFailure on exhausted retries
```

### Partial Failure Handling

If replication to one replica fails but quorum is met — partial success returned. Metadata records only successful nodes. Repair scheduler detects under-replication on next scan and fills the gap.

If stream dies mid-transfer — receiving node's `ChunkWriter.Abort()` deletes the `.tmp` file. Next repair attempt starts fresh.

## 9. Node Join / Leave / Crash

### Node Joins

1. Node starts, scans local disk, compiles chunk inventory
2. Calls `RegisterNode` with inventory
3. Metadata adds to `NodeRegistry`, schedules reconciliation after 30s delay
4. Reconciliation: for each chunk node reports, check against canonical replica list
    - Node has chunk but not in canonical list → schedule eviction (stale replica)
    - Metadata expected chunk on node but node doesn't have it → remove record, trigger repair
5. Node becomes eligible for new chunk placement immediately

### Node Leaves (graceful)

1. Calls `DeregisterNode`
2. Metadata marks node draining — no new placements
3. Metadata triggers repair for all chunks on this node
4. Node drains active RPCs via `GracefulStop`

### Node Crashes

1. Heartbeats stop
2. `NodeWatcher` marks Suspect after 9s (3 missed beats), Dead after 15s
3. `triggerRepair` fires — scans all chunks on dead node, enqueues repair jobs for under-replicated ones
4. gRPC connections to dead node transition to `TransientFailure` within ~13s (application keepalive)
5. `PeerDialer.isHealthy()` returns false, re-dial attempted, fails, repair path takes over

### Over-Replication After Node Returns

Node returns after repair already ran → chunk now exists on more nodes than replication factor.

Resolution during reconciliation:

- Chunk canonical list = [A, D, E] (post-repair)
- Returning node B reports chunk in inventory
- B not in canonical list → eviction instruction sent to B
- B deletes chunk, state is clean

**Canonical replica list in metadata FSM is always the source of truth. Nodes conform to it, not the other way around.**

## 10. Key Design Decisions (Summary)

| Decision | Choice | Reason |
| --- | --- | --- |
| Chunking strategy | Fixed size | Simple, predictable |
| Chunk size | 4MB default, configurable | Sweet spot for parallelism vs metadata overhead |
| Chunk ID | SHA256(file_id + chunk_index) | Known before upload, no content read needed |
| chunk_index storage | Implicit array position in file record | No separate field needed, reassembly is trivial |
| Directory layout | Two-level sharding (ab/12/...) | Scales to millions of chunks without inode limits |
| Write strategy | tmp → fsync → atomic rename | Crash safety — no partial chunks ever visible |
| Replication trigger | Primary node owns fan-out | Keeps metadata lightweight, no per-chunk coordination |
| CommitChunk caller | Storage node, not client | Metadata only records confirmed durable state |
| Repair job delivery | Piggybacked on heartbeat response | Metadata never opens connections to storage nodes |
| Connection pooling | RWMutex + health check + keepalive | Reuse connections, detect dead peers fast |
| Concurrency limit | Semaphore on outbound streams (max 8) | Prevent disk/network saturation |
| Retry jitter | Random jitter on backoff delay | Prevent thundering herd after mass failure |
